# Performance measurement boundaries

This note defines what an external load harness can measure without changing EasyDapper's public API or production code. It does not contain benchmark results.

Use one monotonic clock (`Stopwatch.GetTimestamp`) for the public operation and provider events. Record request start immediately before calling EasyDapper and request end after the returned task or buffered result completes. Keep warm-up, fixture creation, and connection setup outside a steady-state sample unless the scenario explicitly measures connection opening.

| Metric | Measurement | Interpretation |
| --- | --- | --- |
| Operation duration | Public call start to completion | Includes preparation, connection opening if necessary, admission waits, SQL execution, result reads, mapping, and callbacks. |
| Pre-command latency | Public call start to the first native command's `WriteCommandBefore` | Includes preparation, scheduling, opening, and gate waits. It is **not a direct measurement of gate wait**. |
| Provider execution duration | Matching native command `WriteCommandBefore` to `WriteCommandAfter` or `WriteCommandError` | The provider's Execute call. For ExecuteReader, the end event can occur before row consumption and mapping finish. It is **not server-only SQL time**. |
| Connection opening duration | Matching connection open Before to After/Error | Includes the provider's open work, such as pool acquisition. It does not expose EasyDapper's opening semaphore wait. |
| Unattributed remainder | Operation duration outside the union of observed native execution intervals | Client work and unobserved work. It must not be labelled pure lock wait or CPU time. |

For net8 consumers using System.Data.SqlClient, subscribe to `DiagnosticListener.AllListeners`, then `SqlClientDiagnosticListener` and the `System.Data.SqlClient.WriteCommandBefore`, `WriteCommandAfter`, and `WriteCommandError` events. Associate the event's `OperationId` with the operation record established by the harness, for example through `AsyncLocal`. Capture identifiers and the timestamp in the event handler, then aggregate outside it. Enable Before as well as the matching completion events so the provider supplies a usable operation ID. Validate emitted event counts on the actual runtime; absence of diagnostics is missing data, not zero execution time.

The inspected provider source emits the reader completion event when ExecuteReader returns a reader. Its async implementation can also complete the returned task before publishing After. Consequently, a report must allow final events to arrive, match them by operation ID, and report unmatched events. Pre-cancelled calls can produce an unmatched Before. Commands started by a callback belong to the enclosing request unless the harness explicitly creates a child operation. Multiple or overlapping command intervals require interval-union accounting rather than subtracting their summed durations. SqlBulkCopy and query construction require separate coverage; command events do not establish their full duration.

These event boundaries are verified in the primary [System.Data.SqlClient diagnostic event source](https://raw.githubusercontent.com/dotnet/corefx/release/3.1/src/System.Data.SqlClient/src/System/Data/SqlClient/SqlClientDiagnosticListenerExtensions.cs) and [SqlCommand execution source](https://raw.githubusercontent.com/dotnet/corefx/release/3.1/src/System.Data.SqlClient/src/System/Data/SqlClient/SqlCommand.cs). This source inspection defines a measurement strategy, not a claim that every target framework emits the same events. The harness must verify its selected package and runtime.

One EasyDapper service owns one connection and its managed transaction. Independent callers to that same service share the operation gate; command preparation can take place outside that gate to preserve consumer callback behavior. A public operation may acquire admission more than once. MARS and multi-result callback handling can release admission before user mapping finishes. Neither CLR Monitor contention counters nor the time to the first SQL event identifies each SemaphoreSlim admission wait.

Keep the operation gate and connection ownership intact during optimization. Opening another connection for each command changes transaction participation and workload topology. Report a shared-service scenario separately from a scenario using independent services and pooled connections. Compare each with a direct-Dapper control having the same connection count, isolation, buffering, workload, and required serialization. For repeatable SQL measurements, report concurrency, completed operations per second, latency percentiles, errors/cancellations, row correctness, runtime/provider versions, connection limits, fixture size, and run duration. Independent repetitions and allocations can distinguish a preparation optimization from changes in database or queue load.
